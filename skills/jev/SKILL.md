# jev — 판단을 떠넘긴다

좁은 판단은 LLM이 할 필요가 없다. jev는 텍스트를 만들지 않고 **캘리브레이션된 확률**만
돌려준다. 건당 약 **$0.00004, 300~500ms**.

도구는 **이 SKILL.md 와 같은 디렉터리의 `jev.mjs`** 다. 아래 예시의 `$JEV` 를 그 경로로 읽는다.
한 세션에서 여러 번 쓸 거라면 처음에 한 번 잡아 두면 편하다.

```bash
JEV=~/.claude/skills/jev/jev.mjs     # Claude Code 에 직접 복사한 경우
JEV=~/.agents/skills/jev/jev.mjs     # Codex 에 직접 복사한 경우
# 플러그인으로 설치했다면 그 플러그인의 skills/jev/jev.mjs
```

```bash
node "$JEV" "<판단 대상>" --bool <id> "<질문>"
```

## 언제 넘기나

판단을 내리기 직전에 스스로 확인한다. **셋 다 맞으면 넘긴다.**

1. 답이 **예/아니오 · 정해진 보기 중 하나 · 0~N 점수** 중 하나로 떨어진다
2. 판단에 필요한 정보가 **지금 주는 텍스트 안에** 다 있다
3. 설명이 아니라 **값**이 필요하다

전형적인 신호:

| 상황 | 넘긴다 |
|---|---|
| 파일 200개 중 관련된 것만 추리기 | `--bool relevant` 배치 |
| 테스트 실패가 진짜인지 flake인지 | `--bool flake` |
| 이슈·커밋·로그를 분류 | `--pick kind` 배치 |
| 변경이 위험한지 등급 매기기 | `--score risk` |
| 사람 검토가 필요한지 게이트 | `--bool needs_review` |

**반복될수록 이득이 커진다.** 한 건은 직접 봐도 된다. 30건이면 넘겨라.

## 언제 넘기지 않나

- **코드를 고치거나 글을 쓰는 일.** jev는 만들지 못한다. 판단만 한다.
- **이유를 설명해야 하는 일.** jev는 확률만 준다. "왜?"에 답하지 못한다.
- **텍스트 밖을 봐야 하는 일.** 파일을 읽거나 명령을 실행해야 아는 것은 먼저 읽어서 넘긴다.
- **한 건짜리 사소한 판단.** 호출 왕복이 아깝다.

## 쓰는 법

### 질문을 묶어라

질문 여러 개를 한 번에 보내도 **호출은 한 번, 비용도 한 번**이다. 쪼개 보내면 손해다.

```bash
node "$JEV" "$(cat ticket.txt)" \
  --bool urgent "시간에 쫓기는 요청인가?" \
  --pick team "어느 팀이 맡나?" billing=결제·환불 technical=버그·장애 sales=가격 \
  --score severity "얼마나 심각한가?" 사소함 불편함 업무정지
```

### 여러 건은 배치로

stdin 한 줄에 하나씩. 결과는 JSONL로 나오고 **입력 순서가 유지된다.**

```bash
git diff --name-only main | node "$JEV" --batch \
  --bool relevant "이 파일이 인증 로직과 관련 있는가?"
```

```json
{"input":"src/auth/session.ts","relevant":true}
{"input":"README.md","relevant":false}
```

한 건이 실패해도 나머지는 살아남고, 그 줄만 `{"error":...}`로 나온다.

### 셸에 끼우기

`--quiet`는 값만 출력한다.

```bash
if [ "$(node "$JEV" "$(git log -1 --format=%B)" --quiet \
        --bool ok "커밋 메시지가 무엇을 왜 바꿨는지 설명하는가?")" = "false" ]; then
  echo "커밋 메시지를 다시 쓰세요"
fi
```

## 질문 쓰는 법이 정확도를 결정한다

**jev는 틀리지 않는다.** 모호한 질문에는 모호한 답이 아니라 **확신에 찬 엉뚱한 답**이 돌아온다.

여러 건을 처리할 때는 **한 건 기준으로** 물어라. 이걸 빠뜨려서 크게 틀린 적이 있다 —
"리뷰 10만 건을 분류" 작업에서 난이도를 물었더니 jev가 **처리 건수를 난이도로 읽어**
1.55/2를 매겼다. 리뷰 한 건을 분류하는 일은 사소한데도. 질문에 `ONE`을 명시하자 0.21로 교정됐다.

- 나쁨: `"이 작업은 어려운가?"`
- 좋음: `"이 항목 **하나**를 처리하는 게 어려운가? 전체 건수는 무시하라."`

보기에는 설명을 붙여라. `billing=결제·환불·인보이스`가 `billing`보다 정확하다.

## 확신도가 낮으면 멈춘다

`--pick`과 `--score`는 `confidence`를 함께 준다. **60% 미만이면 CLI가 경고를 찍는다.**

```
team           billing  (71% · technical 14%, sales 14%)
               ⚠ team 확신도가 낮습니다. 사람이 보는 게 낫습니다.
```

이때는 **조용히 1순위로 진행하지 않는다.** 사용자에게 후보를 보여주고 고르게 하거나,
그 항목만 직접 읽어본다. jev가 확신도를 주는 이유가 이것이다 — LLM은 근거 없이 단언한다.

## 키 설정

둘 중 **아무거나 하나**면 된다.

```bash
export TYPESAFE_API_KEY="..."        # https://console.typesafe.ai/keys
export AI_GATEWAY_API_KEY="vck_..."  # https://vercel.com/ai-gateway
```

키가 없으면 CLI가 실패한다. 그때는 이 안내를 사용자에게 전달하고,
**추측으로 판단을 대신하지 않는다.**
